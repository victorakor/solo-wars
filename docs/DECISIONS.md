# Decisions

| # | Decision | Alternatives | Reason |
|---|---|---|---|
| 1 | `@arena/shared` exports TypeScript source directly (no pre-build). | Build to `dist` with tsc. | Vite, tsx and Vitest all consume TS directly; avoids a build-order step in `pnpm dev`. Revisit for Docker production image if needed. |
| 2 | Server runs via `tsx` in dev and prod for now. | Compile to JS. | Simplest for Phase 0; production compile step is added in Phase 12. |
| 3 | ESLint 9 flat config with typescript-eslint recommended. | Legacy `.eslintrc`. | Legacy format is deprecated in ESLint 9. |
| 4 | Player collider is a vertical **AABB** (0.8 m square footprint) for world collision; the capsule is used for hit detection from Phase 4. | True capsule-vs-AABB sweep. | Axis-separated AABB sweeps cannot tunnel or snag on box seams, are fully deterministic, and are cheap enough to run for prediction. Slight corner conservatism (~0.17 m) is acceptable. |
| 5 | Movement sweeps in sub-steps of at most 0.1 m per axis. | Single swept test per tick. | Guarantees no tunnelling at sprint or terminal fall speed; verified by the 10-minute fuzz run. |
| 6 | Foundry catwalks are one deck per long side at y=4 (the bridge height), with 10-step stairs (0.4 m rise, 0.55 m run) at all four corners. | Two stacked catwalk levels per side. | The spec's "two catwalk levels" was read as one per long side; the bridge joins both at 4 m. Revisit when the power-pad layout is tuned in Phase 4/5. |
| 7 | Ray queries scan all boxes linearly for now. | Grid or BVH raycast. | About 100 boxes; fine for one camera ray per frame. Server hitscan needs a grid walk, planned for Phase 4. |
| 8 | Scene geometry is a TypeScript module, not JSON. | JSON scene files. | Keeps stairs generated from rules; export to JSON when more scenes arrive. |
| 9 | New combat code lives in `packages/shared/src/sim/`; Phase 1 files (`movement`, `collision`, `scenes/`) stay where they are. | Move everything under `sim/` as the spec's tree shows. | Avoids a pure-churn diff in Phase 2. Move when Phase 3 touches those imports anyway. |
| 10 | Hit detection (head sphere r 0.22 at eye height, body capsule r 0.4) is implemented now, in Phase 2, not Phase 4 as decision 4 anticipated. | Wait for Phase 4. | The Phase 2 exit criteria need real headshot/body hits on a dummy. Movement collision is unchanged (still the AABB from decision 4). |
| 11 | Head sphere has priority: any ray that touches it is a headshot, even if the body capsule is entered first. | First surface hit wins. | The head sits inside the capsule, so first-hit-wins would make side-on headshots impossible. |
| 12 | Spread is a cone sampled uniformly over a disc, seeded by `(matchSeed, shotId, shooterIndex)`. Shotguns sample one aim offset per trigger pull plus an independent 4 degree offset per pellet. Moving x1.25, airborne x2, crouched x0.75 on top of hip/ADS values. | Gaussian spread; no movement modifiers. | Deterministic for client prediction and server resolution (spec 8.1). The movement modifiers are an addition: the spec lists only hip and ADS values, and without them strafing costs nothing. Tune in `COMBAT.spread`. |
| 13 | Recoil is simulated inside the shared sim, not sent by the client. Fire direction = raw aim + sim recoil. Recoil pitch accumulates (capped 15 deg), holds ~1.25 shot intervals after the last shot, then recovers linearly. | Client sends final view angles including recoil. | Recoil stays server-checkable and a "no recoil" client cannot cheat. The camera shows `actor.recoil`. |
| 14 | Over-the-shoulder aim uses a convergence trace (`convergeAim`): the client finds what the camera ray hits and sends the raw aim angles that make the eye-origin bullet pass through that point. | Fire parallel to the camera; or fire from the camera. | Parallel fire misses the crosshair by the 0.75 m shoulder offset at every range (tested). The server still fires from the eye as the spec says; only the angles differ. |
| 15 | Fire rate keeps fractional cooldown carry-over (`cooldown += 60/rpm`). | Reset cooldown to the interval each shot. | At 60 Hz a 780 rpm weapon would otherwise round to 720 or 900 rpm. Tested over 10 s for every weapon. |
| 16 | Superseded by 23. Originally a debug rack on keys 1-5. Burst fire is still not implemented because no weapon uses it. | n/a | n/a |
| 17 | Values the spec leaves open, all in `balance.ts`: head multipliers (Sidearm 1.6, Rattler 1.4, Vanguard 1.5, Breaker 1.3, Longshot 150/95), per-weapon recoil and ADS numbers, `moveSpeedMult` (1.0 / 0.98 / 0.95 / 0.93 / 0.85), Longshot has no range falloff, damage is capped at remaining health for stats. | n/a | The spec gives damage, rpm, magazine, reload and falloff; everything else is a first-pass tuning guess to be adjusted by playtest in Phase 12. |
| 18 | The practice bot lives in `shared` (not `server/src/ai`) and produces the same `ActorInput` as a human. It knows its target's position (no vision or hearing model) but only shoots with line of sight, reacts after a delay, has aim error, and escapes when stuck. Navigation is straight-line. | Server-only AI now. | The client needs it locally in Phase 2; the server reuses it unchanged in Phase 3 and Phase 10 adds real navigation. |
| 19 | Mouse capture is explicit: pointer lock is requested only from the menu's Play/Resume button or the P key, never by clicking the game. Esc (browser), P, losing window focus or tab visibility, and Quit all release it, and the simulation pauses whenever it is released. | Capture on any click (Phase 1). | Phase 1 grabbed the mouse on the first click with no menu, which made safe exit difficult. P is an extra escape hatch for setups where Esc is swallowed. |
| 20 | Foundry gained two more mirrored spawn pairs (6 total, point-symmetric). | Keep 2 spawns. | Spawn selection (farthest without line of sight, spec 5.3) needs several candidates. Full scene tuning stays in Phase 5. |
| 21 | Bot movement upgrade after playtest feedback: strafes in short varied bursts with brief stops (crouching at range), never strafes into walls, pushes when its target is reloading or low, backs off when hurt, rolls away when shot (`dodgeChance`), jump-strafes (`jumpiness`), and detects "hunting but not closing in" so it no longer slides along walls. Still straight-line navigation with a more-open-side escape; real pathing stays in Phase 10. | Leave it as shipped. | The first version spent long stretches walking one way and got pinned against cover. |
| 22 | Hold-to-fire is a client input option (default on, key H): while the button is held, semi, pump and bolt weapons receive a fresh press every tick, and the sim's cooldown still enforces each weapon's rpm. | Change the weapon rules so semi weapons auto-fire; or leave one click per shot. | Playtest feedback: holding the button should keep firing. Keeping it client-side leaves the shared weapon rules and the future server check (rate cannot exceed rpm) untouched. |
| 23 | Weapon slots and floor pickups were pulled forward from Phase 4 after playtest feedback. Slot 1 is the weapon you choose (unlimited reserve, full magazine on respawn); slot 2 is a picked-up firearm with limited ammo that disappears when empty. Walk over a pad into an empty slot to pick up, E swaps when full (the old weapon drops at your feet and cannot be retaken until you step away), X drops, 1/2/wheel switch. Pads respawn 25 s after being taken (first drops after 3 s in this practice mode), mirrored pads roll the same item, rarity 60/30/10 gives x1/x1.15/x1.3 damage and +0/10/20% magazine, drops despawn after 15 s, and the carried floor weapon drops where you die. | Wait for Phase 4. | Needed for the requested pick-up and switch behaviour. Follows spec sections 5.4 and 7; Hellfire, melee, grenades and medkits are still Phase 4. |
| 24 | The range is a free-for-all. Bots fight whoever is nearest and visible (you or other bots), switch between their two weapons by range, detour to pick up weapons when their second slot is empty, and respawn forever. Bots are added one at a time (B, or the menu) with random loadouts, up to 10. Stationary dummies remain only as an option for tests. | Keep the stationary targets. | Playtest feedback: stationary targets are not useful for fighting practice. |
| 25 | Before a fight you pick your weapon on the start screen; while dead, keys 1-5 choose the weapon for your next life. The weapon you choose applies at your next respawn, or immediately with Restart. | Switch weapon mid-life from the menu. | Keeps the rule that your loadout weapon is fixed for a life, as in the spec. |
| 26 | When a floor weapon leaves the rack (death drop, swap, X, empty) the selected slot is reset to the loadout weapon, `nearPickup` is validated at the end of every tick, and the client render loop queues its next frame first and reports an error once instead of dying. | n/a | Bug found in playtest: dying while holding a floor weapon left the dead actor pointing at a removed slot and froze the client. Covered by a regression test and a 3-minute chaos test that checks weapon, ammo and slot invariants every tick. |
| 27 | Netcode logic is transport-free: client prediction, interpolation, clock sync and the whole `NetClient` live in `shared/net`; the authoritative `MatchCore` lives in `server/net`; the Colyseus classes are thin adapters. | Put logic in the Colyseus room and client. | It can be run and tested end to end over a simulated lossy link with a virtual clock, which is the only way to test netcode properly. The adapters are small enough to review by eye. |
| 28 | Fire, reload, weapon switch, pickup, drop and dodge are flags inside input frames, not separate messages as spec section 9 lists. | Separate `fire` etc. messages. | They are ordered with movement, predicted identically, and cost no extra packets. Lag-compensation time rides in the input batch header. |
| 29 | A batch carries the last 4 inputs, not 3. | 3, as in the spec. | At 30 Hz batches of 60 Hz inputs, 3 leaves every second input sent once; measured 2.8% of inputs lost at 5% packet loss (a lost press means a shot that never happens). 4 gives 0.55%. |
| 30 | The server runs one input per player per tick with a catch-up credit budget (8), and stalls when starved. | Run each input when it arrives; or repeat the last input when starved. | Bounded: a flooding client cannot move faster than real time (tested). Deterministic: the server never invents an input, so the client's replay matches exactly. |
| 31 | The owner's body and combat state are sent in full every snapshot with exact float timers. Other players use a slow-field mask. | Quantised millisecond timers; changed-fields for the owner. | Millisecond rounding made predicted shots flip a tick early or late (client drew 108 or 134 shots for 120 real ones under jitter). Exact floats fixed it for about 28 bytes. |
| 32 | Wire squeezing to stay inside 15 kbps up: consecutive sequence numbers are implicit, aim is only sent on inputs that fire, aim deltas are 12-bit (0.017 degree steps, +-0.6 rad), the client clock is 16 bits, the roll direction is sent only while rolling. | Fixed 16-byte inputs. | Continuous fire with aim measured 17.4 kbps up before; 14.5 after. |
| 33 | Lag compensation: 1 s hitbox history, rewind clamped to 250 ms, never blended across a respawn (epoch), shooter's render time is its server-clock estimate minus the 100 ms interpolation delay. | Rewind by half the measured RTT. | What the shooter saw is the right thing to judge. Measured: 98% of shots at a strafing target land at 0, 80 and 150 ms and 96% at 250 ms; without rewind 45%, 29%, 22%, 17%. |
| 34 | A room holds 2 humans and at most 2 bots; a room with bots goes live when the first human joins, otherwise when the second does. Pause (3 s silence, 30 s grace) and forfeit exist; the rest of the lifecycle is Phase 6. | Up to 4 bots. | Each extra actor costs about 3 kbps downstream; 2 humans + 2 bots measures 28.4 of the 30 kbps budget. |
| 35 | Opening the menu while online does not pause: the player stands still and keeps sending idle inputs. | Stop sending inputs. | If inputs stopped, the server would treat the silence as a disconnect and pause the match for the other player. |
| 36 | The client asks for the welcome again (`hello`) until it arrives. | Trust the first welcome. | It is sent during the join, possibly before the client is listening; I could not check Colyseus's delivery order here, so a missed welcome must not strand the player. |
| 37 | The Colyseus adapter and the colyseus.js connection are verified only by typechecking against stubs I wrote from memory of the 0.16 API, plus `pnpm smoke:match`. | n/a | The build sandbox had no network, so the real packages could not be installed. Everything under them (about 100 tests) runs against the real code. |
